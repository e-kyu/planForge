# /plan-doc — 문서 콘텐츠 기획서(plan.md) 생성

$ARGUMENTS

기획 문서(제안서·개발설계서 등)의 콘텐츠 기획서 `plan.md`를 만든다. plan.md는 모든 포맷(PPT·md·html·docx)의 원본이다. 코드를 작성하지 않는 단계다.

## 절차

0. **프로젝트 결정**: `$ARGUMENTS`를 프로젝트명으로 해석해 `<P>` = `projects/<프로젝트명>/`로 확정한다. 인자가 없으면 `projects/*/plan.md`를 나열해 사용자에게 선택받는다(1개여도 확인). 규칙 상세는 `CLAUDE.md`의 "프로젝트 결정 규칙" 참조.
1. **소스 확인**: 루트 `sources/`(글로벌 자료)와 `<P>/sources/`(프로젝트 고유 자료), 그리고 `<P>/docs/interview-log.md`를 먼저 읽는다.
2. **가설 선제시**: 질문을 던지기 전에 소스·기존 팩트·대화 맥락에서 도출한 **예상 뼈대 초안**을 먼저 제시한다. 항목: 산출 문서 목록(제안서만 / 개발설계서만 / 둘 다) / 목적 / 청중(직책·관심사) / 예상 분량 / 핵심 메시지 후보 3개 / 예상 구성(슬라이드 또는 문서 섹션). 사용자는 질문에 답하는 대신 이 초안을 확인·수정·반박한다.
   - 맞는 부분은 질문 없이 확정으로 전환하고, 틀린 부분만 정밀 질문 대상이 된다.
   - 인터뷰 시작 시 총 예상 라운드 수와 예상 소요 시간(5~10분)을 함께 안내한다.
3. **인터뷰 (가변 라운드)**: 초안에서 미확정·반박된 부분만 AskUserQuestion으로 정밀 질문한다. 한 번에 최대 4개, 답변을 파악한 뒤 다음 라운드.
   - 표준 라운드 순서는 "뼈대(목적/청중/분량/시한) → 내용 → 근거(데이터 유무·가정)"이며, **내용 라운드는 산출 문서에 따라 아크가 다르다**:
     - **제안서 아크**: 문제 / 해결책 / 기대효과
     - **개발설계서 아크**: 배경·요구사항 → 시스템 구성·인터페이스 → 데이터·모듈 설계 → 일정·리스크
   - 산출 문서가 둘 다면 두 아크를 모두 진행한다. 요구사항·시스템 구성·일정 같은 팩트는 두 문서가 공유하므로 interview-log에 중복 없이 적립한다.
   - 가설 선제시에서 이미 확정된 항목은 건너뛴다.
   - **핵심 메시지 확정 라운드**: 라운드 2 종료 시점에 핵심 메시지 3개 후보를 제시해 사용자 승인을 받는다. 이후 라운드의 목표는 "이 3개를 성립시킬 근거 수집"이다.
   - **질문 설계 규칙**: 질문당 1개 주제. 선택지는 상호배타적이고 실제 사례 기반으로 구성하고, 왜 이 옵션들을 올렸는지 근거를 옵션 설명에 포함한다. 문제 정의 같은 서술형이 필요한 것은 한 라운드에 모아 자유 서술을 유도한다.
   - **모순 처리**: 이전 답변과 충돌하는 답이 나오면 즉시 확인한다. 조용히 최신값으로 덮지 않는다.
   - **라운드별 즉시 팩트 확인**: 각 라운드가 끝날 때마다 그 라운드에서 확정된 팩트를 3~5줄 요약으로 보여주고 "이대로 기록할까요?" 확인 후 적립한다. 적립 전에 다음 라운드로 넘어가지 않는다.
4. **종료 판정**: 산출 문서별 체크리스트가 모두 충족되면 인터뷰를 종료한다. 미달이면 부족한 항목만 추가 라운드로 물어본다.
   - [ ] 목적·청중·분량·제출 시한 확정 (공통)
   - [ ] 미확정 목록이 있으면 "언제까지·어떻게 확인할지"까지 질문 완료 (공통)
   - 제안서: [ ] 핵심 메시지 3개 후보 사용자 승인 / [ ] 각 메시지에 근거 확보 (로그 항목 또는 `(미확정)` 명시)
   - 개발설계서: [ ] 요구사항 목록 확정 / [ ] 시스템 구성 슬라이드(`[유형: 구성]`) 확보 / [ ] 인터페이스·데이터 항목 근거 확보 / [ ] 일정·리스크 기재
   - 산출 문서가 둘 다면 위 두 체크리스트의 합집합을 충족해야 한다.
5. **팩트 적립**: 인터뷰에서 확정된 내용을 `<P>/docs/interview-log.md`에 날짜와 함께 기록한다. (파일이 없으면 헤더를 만들어 시작) 인터뷰 중 확인 필요가 드러난 항목은 미확정 섹션에 즉시 적립한다.
6. **plan.md 작성**: `<P>/plan.md`에 작성하며 `CLAUDE.md`의 plan.md 포맷을 그대로 따른다.
   - 메타에 `산출 문서`를 기록 (제안서 1개뿐이면 생략 가능 — 기본 제안서)
   - 핵심 메시지는 정확히 3개 (인터뷰에서 승인받은 후보 기준)
   - 각 슬라이드에 `유형` 표기 (표지/목차/2단/표/차트/구성/마무리 중 하나) — 유형 표기는 PPT 개조식 관점의 뼈대이며, 문서 포맷은 이를 섹션 구조로 해석한다
   - 산출 문서가 여러 개면 `CLAUDE.md`의 문서 태그 규칙을 따른다: 슬라이드 제목 행에 `[문서: ...]` 태그, 표지·목차·마무리는 문서별 별도 슬라이드, 각 문서의 목차 불릿은 그 문서에 포함되는 슬라이드만 01..NN 재채번
   - 근거가 없는 수치는 `(미확정)`으로 명시 — 확정 전에 흐리면 안 된다
7. **검수 요청**: plan.md 전문을 보여주고 "이대로 진행할지, 수정할 부분이 있는지" 사용자에게 확인받는다. 승인 전에 make 커맨드로 넘어가지 않는다.

## 주의

- 기존 plan.md가 있으면 덮어쓰기 전에 내용을 보여주고 확인받는다.
- 슬라이드당 메시지 1개 원칙을 유지한다.
- 가설 선제시는 가설일 뿐이다 — 소스·팩트가 텅 비어 있으면 초안을 만들지 말고 뼈대 질문부터 시작한다. 임의 추측을 확정처럼 제시하지 않는다.
- 소스·기존 팩트가 풍부한 프로젝트는 인터뷰가 1~2라운드로 끝나는 것이 정상이다. 3라운드를 채우려고 하지 않는다.
